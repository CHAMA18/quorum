## 2. Executive assessment

Quorum is a genuinely ambitious and unusually well-engineered prototype. The governance core — hash-chained audit spine, signed epochs, Ed25519 gate receipts, single-use step-up tokens, attested gateway identity, fail-closed office/quorum checks, and honest evidence labelling — is better than most production procurement tooling. The domain model is deep, the edge and desktop hardening are credible, and the documentation is candid about what is not measured.

The gap is between that strong core and the *edges* around it: dependency hygiene, deployment reproducibility, privacy, multi-workspace isolation, and the last mile of a few user flows. In its current state Quorum is an excellent demo with several release-blocking defects, not a system that should process a real institution's procurement data.

| Domain | Rating | One-line verdict |
|---|---|---|
| Procurement domain logic & governance | **Strong** | Deep, deterministic, evidence-linked; a few authority shortcuts remain |
| Auditability & evidence integrity | **Strong** | Hash chains, anchors, receipts, export package, verification tooling |
| Authentication | **Good** | scrypt, opaque sessions, TOTP, step-up; some lifecycle gaps |
| Authorization & tenancy | **Weak** | Role matrix is sound; workspace isolation is incomplete |
| Privacy & data protection | **Poor** | Session replay, third-party analytics, no consent, weak at-rest protection |
| Secrets & cryptography | **Good** | Purpose-scoped HMAC, Ed25519, fail-closed defaults |
| Data durability | **Adequate** | Strong sidecar writer discipline; web store is an unlocked JSON file |
| API security | **Mixed** | Good patterns on most routes; unauthenticated paid/process surfaces |
| Frontend craft | **Good / poor modularity** | Accessible intent and polish inside 11k-line components |
| Accessibility | **Promising, unverified** | 479 aria-labels, skip links, focus trapping; no automated or manual audit |

## 3. Top risks (read these first)

1. **Critical Next.js RCE advisories** on `next@16.1.1` (Image Optimization AVIF/SVG, `use cache`, Windows RCE) and an unused `next-auth@4.24.13` with a critical homoglyph bypass. See Q-01.
2. **Unauthenticated, unthrottled paid AI endpoints** — `/api/muse/speak` and `/api/muse/transcribe` let anyone on the internet spend the deployment's Cloudflare/Meta budget. See Q-02.
3. **Unconditional LogRocket session replay** across sign-in and the procurement workspace, with no masking configuration or consent. See Q-03.
4. **Incomplete workspace isolation** — the app can create multiple workspaces, but committee roster, settings, supplier register, oversight events, tender files, and gate notifications are global. See Q-04.
5. **Office authority is bypassable by the officer path** — any OWNER/ADMIN/OFFICER can sign an office-specific gate under their own name; an OWNER can also mark quorum present, so one person can manufacture quorum and sign. See Q-05.
6. **The production container cannot build** — `Dockerfile` runs `npm ci` against a stale lockfile. See Q-06.
7. **CI is red and under-specified** — lint fails, and CI never runs typecheck, the full web suite, a build, or an audit. See Q-07.
8. **Supplier password reset is broken in the UI** — the screen expects an 8-character code; the API now sends a Firebase email link and returns no code. See Q-08.

## 4. What is genuinely world-class (preserve this)

- **The audit spine.** `appendLog` hash-chains every call; `log-segments.jsonl` seals signed epochs; `log-anchors.jsonl` seals daily heads; `verifyToolLogFile` refuses new decisions when the chain does not verify. This is a real tamper-evidence design, not a log table with a checksum column. (`mini-services/quorum-mcp/store.ts`, `index.ts`)
- **The gate.** Named-human approval, office binding for roster members, step-up token bound to `gateId + docHash + actor`, single-use `jti`, dual approval above a threshold, separation-of-duties against preparers, conflict-of-interest exclusion, sitting-based quorum, and a signed Ed25519 receipt with `evidential` status surfaced honestly. (`mini-services/quorum-mcp/index.ts:500-760`, `cycle-routes.ts:642`)
- **Attested identity.** The browser cannot name the actor; the Next gateway derives it from the verified session and HMAC-seals method/path/actor/workspace/timestamp. The sidecar rejects unattested mutations. (`src/app/api/[...path]/route.ts`, `src/lib/sidecar-attest.ts`, `store.ts:429`)
- **Purpose-scoped secrets.** `ATTEST_SECRET`, `STEP_UP_SECRET`, `DOWNLOAD_SECRET`, `NOTIFY_SECRET`, `AUDIT_SECRET`, `MUSE_ACTION_SECRET`, `BID_VAULT_SECRET`, each falling back to `GATE_SECRET`, with a production hard refusal instead of a dev default. (`src/lib/secrets.ts`, `mini-services/quorum-mcp/secrets.ts`)
- **Fail-closed patterns.** Unreadable committee roster → 503, never "present". Short roll → 409. Invalid audit chain → no new decision. Missing step-up → 403. Unknown sidecar path → 404. (`index.ts`, `src/lib/permissions.ts`)
- **Document storage hardening.** Path traversal validated three ways (`isSafeTenderRef`, `isTenderKeyFor`, resolved-prefix check), signed five-minute, user-bound downloads, range handling, content-type/`nosniff`, and an audit line per delivery. (`src/lib/tender-local-store.ts`, `tender-access.ts`, `docs/download/route.ts`)
- **Edge worker.** Constant-time shared-secret checks, key/prefix validation, byte-range correctness, authenticated MCP bearer path, no wildcard CORS on data routes. (`workers/quorum-edge/src/index.ts`)
- **Desktop shell.** `contextIsolation`, `sandbox`, no `nodeIntegration`, navigation allowlist, external links handed to the OS. (`desktop/main.cjs`)
- **Honest documentation.** The README's Limitations section admits single-labeller evaluation, unmeasured human impact, simulated e-GP, and single-writer deployment. That is rare and should stay.

## 5. Findings — P0 (release blockers)

### Q-01 · Critical vulnerable framework dependencies
**Severity:** Critical · **Area:** supply chain · **Evidence:** `bun audit`, `npm audit`

`next@16.1.3` (declared `^16.1.1`) is inside the affected range of several critical advisories, including unauthenticated RCE in the Image Optimization API (AVIF and SVG paths) and `use cache` typed-array RCE, all fixed in `16.3.3`/`16.4.1`. `next-auth@4.24.13` carries a critical email-normalization homoglyph bypass (`<4.24.15`). `next-auth` is **not imported anywhere in `src/`** — it is an unused dependency expanding the attack surface. `zod@4.3.5` (via direct and LangChain/MCP) is below the fixed `4.6.6`.

**Impact:** Remote code execution or DoS against a self-hosted deployment, plus unnecessary auth-library exposure. Public-sector procurement data is a high-value target.
**Fix:** Upgrade `next` to the latest 16.x (≥16.4.1), upgrade or remove `next-auth`, upgrade `zod`; regenerate `bun.lock`; add `bun audit --production` as a blocking CI step. Re-test the App Router build after the framework jump.

### Q-02 · Unauthenticated paid AI endpoints
**Severity:** Critical (financial abuse) · **Area:** API · **Evidence:** `src/app/api/muse/speak/route.ts:32`, `src/app/api/muse/transcribe/route.ts:39`

Neither route checks a session, and neither rate-limits. `speak` proxies up to 1,400 characters per request to Deepgram Aura-2 via the edge worker; `transcribe` proxies up to 12 MB of audio to Meta Muse Voice (or edge ASR). Anyone who finds the URLs can burn the operator's quota/budget indefinitely. `/api/muse/chat` is authenticated but also unthrottled, so a signed-in account can spam model calls.

**Impact:** Direct financial loss, quota exhaustion, denial of service to legitimate users, and a noisy abuse vector on a product that markets cost discipline.
**Fix:** Require a verified officer or org session; add per-user + per-IP distributed limits (the existing `rateLimit` and Upstash limiter are available); cap concurrent calls; consider a feature flag for voice. Add a daily spend guard.

### Q-03 · Unconditional LogRocket session replay of procurement data
**Severity:** Critical (privacy/compliance) · **Area:** privacy · **Evidence:** `src/components/quorum/firebase-analytics.tsx:14`, mounted globally in `src/app/layout.tsx`

`LogRocket.init("1bq4fh/support")` runs for every visitor on every page, including the sign-in screen and the authenticated workspace. There is no consent gate, no `dom.textSanitizer`, no input masking configuration, no opt-out, and no privacy notice in the app. LogRocket's default replay captures DOM text (supplier names, tender references, bid values, notes) and sends it to a US third party. Firebase Analytics is also initialized unconditionally. This directly contradicts the product's redaction/residency posture and is difficult to reconcile with GDPR/Kenya DPA obligations for public-sector data.

**Impact:** Unlawful/undisclosed transfer of procurement and personal data; reputational and contractual exposure; potential evidence-handling breach.
**Fix:** Remove LogRocket from authenticated surfaces immediately. If product analytics are required, gate them behind explicit consent, mask all text and inputs (`dom.textSanitizer: "deep"`, `network.requestSanitizer`), exclude auth and document routes, and disclose the processor. Do the same for Firebase Analytics.

### Q-04 · Incomplete workspace isolation (cross-tenant leakage)
**Severity:** Critical if more than one workspace exists · **Area:** data model · **Evidence:** `src/lib/db.ts`, `src/lib/notifications.ts:285`, `src/app/api/admin/overview/route.ts:264,298`

Registration is public and `createUser` assigns a **new random `workspaceId`** to each self-serve signup after the first, and `roleForNewWorkspaceMember` gives that first member the **OWNER** role (`db.ts:createUser`, `src/lib/role-assignment.ts`). The sidecar is scoped carefully, but the web store is not:

- `listCommitteeMembers()` (`db.ts:1038`) is global — any signed-in user can read every workspace's committee names, roles, and offices via `/api/committee`.
- `getSetting()` (`db.ts:1094`) is global — committee seats, quorum, MFA policy, launch sign-off, and per-tender checklists are shared.
- `listOrganizations()` (`db.ts:1240`) is global — the supplier register is shared, and admin overview exposes it to every tenant (`admin/overview:264`).
- `listOversightEvents()` (`db.ts:787`) is global — governance history is exposed in admin overview (`admin/overview:298`).
- `fanOutGateEvent()` calls `listUsers()` with no workspace filter (`notifications.ts:285`) — a gate in workspace A sends notifications (tender ID, outcome, approver note) to **every verified user in every workspace**.
- Tender document listing/download/ZIP routes authorize by role only, not by workspace, so any `read_documents` user can address another tenant's tender by reference.

**Impact:** Anyone who can register gets their own workspace as OWNER, then reads the first workspace's committee roster, settings, supplier register, governance events, and receives its gate notifications. On the live app this is a self-serve cross-tenant disclosure path, not a theoretical one. This is a data-protection incident waiting to happen.
**Fix (choose one, explicitly):**
1. **Declare single-workspace deployment:** add a `singleWorkspace` mode, reject additional workspace creation, and enforce one workspace in every list function; or
2. **Complete tenancy:** add `workspaceId` to committee members, settings, organizations, oversight events, tender objects and notifications; scope every read; add cross-tenant tests that fail closed. Until then, do not expose registration on a shared deployment.

### Q-05 · Office authority bypass and single-person quorum manufacture
**Severity:** High · **Area:** governance · **Evidence:** `mini-services/quorum-mcp/cycle-routes.ts:658-671`, `engine.ts:2570-2586`

For an office-specific gate, `preApprovalCheck` skips the office check whenever the approver name equals the attested signed-in user (`isOfficer`). Any OWNER, ADMIN, or OFFICER holds `sign_gates`, so they can sign an `ACCOUNTING_OFFICER` gate under their own name without holding that office. `quorumCheck` then adds the signed-in user as the "gavel" if not on the roster, and OWNER/ADMIN can set any committee member `PRESENT` through the committee API. A single OWNER can therefore mark four members present, count themselves as the fifth, complete step-up, and sign an award gate. The README's claim that "a member who does not hold a gate's office is refused (403)" is true for roster members but not for this officer path.

**Impact:** The separation-of-duties story is weaker than documented; a compromised or colluding owner can complete an irreversible act alone. Step-up and audit still apply, so this is not silent — but it defeats the office control.
**Fix:** Bind the gavel exemption to a named office or an explicit `isAccountingOfficer` flag, not to "any signed-in officer". Require a second human for roster changes that create quorum, or make quorum derive from admitted sitting attendance only. Add a test that an OFFICER cannot sign an ACCOUNTING_OFFICER gate without the office.

### Q-06 · Production container build is broken
**Severity:** High (release blocker) · **Area:** deployment · **Evidence:** `Dockerfile:6`, `npm ci --dry-run`

`package-lock.json` is stale: it is missing `@modelcontextprotocol/server-filesystem`, `playwright`, and several transitive packages. `npm ci` refuses an out-of-sync lockfile, so the Docker image cannot build. The local `npm run build` passed only because `node_modules` was already present. The repo also carries both `bun.lock` (used by CI) and `package-lock.json` (used by Docker), which will drift again.

**Impact:** No reproducible production image; deploys depend on an undocumented prebuilt artifact.
**Fix:** Pick one package manager. Regenerate `package-lock.json` (`npm install --package-lock-only`) and verify `npm ci && npm run build` from a clean checkout, or change the Dockerfile to `bun install --frozen-lockfile` and `bun run build`. Add a CI job that builds the image.

### Q-07 · CI is red and does not protect the product
**Severity:** High · **Area:** engineering process · **Evidence:** `.github/workflows/ci.yml`, `npm run lint`

- Lint fails with 2 real errors: `src/components/quorum/compliance-view.tsx:163` and `src/components/quorum/theme-toggle.tsx:90` (`react-hooks/set-state-in-effect`).
- CI runs lint, sidecar tests, **one** web test file (`db-store-isolation`), and the eval harness. It never runs `tsc`, the full web suite, a production build, a container build, or a dependency audit.
- The lint config disables nearly every meaningful rule (`no-explicit-any`, `no-unused-vars`, `react-hooks/exhaustive-deps`, `prefer-const`, `no-empty`, …), so "lint passes" would be weak evidence even when green.
- CI triggers on `main`/PRs only; the active branch is `mirror-integration` with 196 uncommitted paths.

**Impact:** Regressions in the web app and deployment can merge without detection; the current branch cannot go green.
**Fix:** Fix the two errors; run `tsc --noEmit`, `bun run test`, `next build`, a Docker build, and `bun audit` in CI. Re-enable `exhaustive-deps` and `no-explicit-any` incrementally. Add a branch/PR gate for the working branch.

## 6. Findings — P1 (fix before any pilot)

### Q-08 · Supplier password reset UI is broken
**Severity:** High · **Area:** functional · **Evidence:** `src/components/quorum/org/org-auth-screen.tsx:854-889`, `src/app/api/org/auth/forgot-password/route.ts`, `src/app/api/org/auth/reset-password/route.ts`

The screen calls `/api/org/auth/forgot-password` and requires `{ issued, code, expiresAt }`. The route was migrated to Firebase email links and returns `{ sent: true }`; no code is ever issued (`createOrgPasswordReset`/`generateResetCode` are dead code). A valid supplier is told "No organization account holds that address", and `/api/org/auth/reset-password` can never succeed because no code exists. The Firebase-link path does work (org login re-syncs the hash), but the UI never tells the user to check email.

**Impact:** Locked-out suppliers cannot recover their account through the product.
**Fix:** Choose one flow and make the UI match: either remove the code UI and say "check your email for the reset link", or re-introduce a server-issued one-time code (and delete the Firebase mail path). Add a test for the full reset flow.

### Q-09 · Sensitive store is world-readable; session tokens and TOTP secrets are plaintext
**Severity:** High · **Area:** data protection · **Evidence:** `db/quorum-store.json` mode `-rw-r--r--`, `src/lib/db.ts:666`, `SessionRow.token`, `UserRow.totpSecret`

`persist()` writes `db/quorum-store.json` with default umask (observed `0644`). It contains password hashes, live session tokens, TOTP secrets, supplier PII, and support messages. Any local user on the host can read or copy them. Session tokens are stored in plaintext (a read of the store is a session takeover), and TOTP secrets are not encrypted at rest.

**Impact:** Host-level compromise or a misconfigured backup becomes an account-takeover incident.
**Fix:** Create the store with `0600` (and the directory `0700`); store only a SHA-256 of session tokens; encrypt TOTP secrets with a key held outside the store (`TOTP_ENC_KEY`); document file permissions in operations. Audit backup archive permissions too.

### Q-10 · Public process-control and information endpoints
**Severity:** Medium-High · **Area:** API · **Evidence:** `src/app/api/mcp-ensure/route.ts:8`, `src/app/api/agent-status/route.ts:14`, `src/app/api/events/route.ts:15`

- `/api/mcp-ensure` is unauthenticated and can spawn a detached sidecar process if the port is free. Repeated calls are a process/resource DoS.
- `/api/agent-status` is unauthenticated and proxies the sidecar's rich `/api/health` payload (model endpoint, counts, gate-key status, queue state).
- `/api/events` is an unauthenticated SSE stream with no connection cap; each client consumes a timer and a listener.

**Impact:** Resource exhaustion and unnecessary disclosure of operational detail.
**Fix:** Require a session for `agent-status` and `events`; remove `mcp-ensure` from the public surface (let instrumentation own boot) or require an admin session. Cap SSE connections per IP and add a heartbeat/timeout.

### Q-11 · No security headers / clickjacking protection
**Severity:** Medium-High · **Area:** web security · **Evidence:** `next.config.ts`, `Caddyfile`

There is no `Content-Security-Policy`, `Strict-Transport-Security`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, or `Permissions-Policy` configured at either layer. The dashboard and admin console can be framed, and third-party script injection has no CSP backstop.

**Impact:** Clickjacking of approval screens; weaker defense-in-depth against XSS/supply-chain script compromise.
**Fix:** Add headers in `next.config.ts` (`headers()`) or Caddy: CSP with explicit script/style/font/connect sources, `frame-ancestors 'none'`, HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` disabling unused features. Test the app with the CSP enforced.

### Q-12 · Authentication lifecycle gaps
**Severity:** Medium · **Area:** auth · **Evidence:** `src/lib/auth.ts`, `src/app/api/auth/reset-password/route.ts`, `src/app/api/auth/login/route.ts`

- Rate limits are per-IP only; there is no per-account lockout or progressive delay. A distributed attacker can grind a single account.
- Sessions last 30 days with `remember` and have no idle timeout, no rotation, and no revocation on officer password reset. (The supplier reset does revoke org sessions; the officer path does not.)
- `clientKey` trusts the first `X-Forwarded-For` value. Caddy overwrites it, but a deployment behind a proxy that appends rather than replaces is bypassable.
- The JSON-file rate limiter is read-modify-write per process; multiple Next workers can exceed the configured limit.
- Password policy is 8 characters with no breached-password check; TOTP is only mandatory for signing, not for all privileged sessions.

**Impact:** Brute-force and session-hijack risk; limit bypass under scale-out.
**Fix:** Add per-account counters, revoke sessions on password change, add idle timeout, hash session tokens (Q-09), use a shared store for limits (Upstash) in multi-instance deployments, and document proxy trust assumptions. Consider a breach-list check and mandatory MFA for OWNER/ADMIN at sign-in.

### Q-13 · Dependency and lockfile hygiene beyond the criticals
**Severity:** Medium · **Area:** supply chain · **Evidence:** `bun audit`, `package.json`

112 advisories in the bun tree include repeated DoS and prototype-pollution issues in transitive packages (`lodash`, `js-yaml`, `postcss`, `sharp`, `re2js`, `source-map-js`, `picomatch`, `nanoid`, `uuid`). Several are dev-only, but the runtime tree is large and unaudited. `sharp` is a direct dependency with inherited libvips/libheif/librsvg CVEs; verify it is actually needed. There is no SBOM and no automated dependency update policy.

**Impact:** Known exploitable code in the deployed image; upgrade debt compounds.
**Fix:** Produce an SBOM, run `bun audit` in CI, add Dependabot/Renovate, and take a deliberate upgrade pass. Remove unused dependencies (`next-auth`, possibly `sharp`, `@langchain/*` if the sidecar does not need them at runtime).

### Q-14 · Test coverage is broad but ends at the unit boundary
**Severity:** Medium · **Area:** quality · **Evidence:** `package.json`, `tests/`, missing Playwright config

There are 67 test files and 572 passing tests, which is commendable. But there are **zero browser/E2E tests** despite Playwright being a dev dependency; `tests/` contains only Python runtime shell scripts. The most complex surfaces — the 11,219-line dashboard, the 8,159-line cycle view, the supplier console, the gate signing modal, the reset flows — are untested end-to-end. 13 live R2 tests are skipped, so the storage gate is not exercised in CI. The evaluation harness is narrow and single-labeller (documented).

**Impact:** Regressions in the highest-risk user journeys (sign-in, upload, gate signing, supplier filing) are invisible until a human clicks through.
**Fix:** Add a small, stable Playwright suite: login → upload → run → gate refusal → step-up → signed receipt; supplier register → apply → withdraw; reset flow. Run it against the isolated judge stack in CI. Add one axe accessibility check per primary screen.

### Q-15 · Historical `DATABASE_URL` in git history
**Severity:** Medium · **Area:** secrets · **Evidence:** commit `1eb3498` (`.env`)

The initial commit included `.env` with a `DATABASE_URL` (49 bytes, no embedded password; removed in `9920838`). It remains in history. No other tracked secrets were found; `.env*`, `*.pem`, and the local store are ignored.

**Impact:** If that URL ever named a real database/role, it is public in the repository history.
**Fix:** Confirm and rotate the credential; if the repository is public, consider history rewrite (with the usual coordination) or at minimum document the exposure. Add secret scanning (gitleaks/TruffleHog) to CI.

## 7. Findings — P2 (hardening, scale, and polish)

### Q-16 · Web store is an unlocked, whole-file JSON store
`src/lib/db.ts` caches the entire store in memory and rewrites the full JSON file on every change. The sidecar has a writer lock; the web store does not. Two Next processes (or a dev server plus a standalone server) will silently clobber each other; every session lookup, notification, or role change rewrites ~1.5 MB. This is acceptable for a single-process demo and explicitly documented as single-writer, but it is not a multi-instance design. Move accounts/sessions/committee/settings to Postgres before institutional deployment, or add an exclusive lock and a documented single-process constraint.

### Q-17 · No error boundaries, loading states, or not-found pages
`src/app` has no `error.tsx`, `global-error.tsx`, `not-found.tsx`, or `loading.tsx`. A server-side failure in `/admin`, `/docs`, or `/award/[ref]` falls through to the framework default; a failed client fetch can leave a panel blank. Add route-level error boundaries with a retry action and a support reference, plus a branded 404.

### Q-18 · Observability stops at trace IDs
The sidecar has excellent trace IDs, audit health, queue summaries and a verification endpoint. The Next layer has no structured request logging, no error tracker (LogRocket is session replay, not error monitoring), no metrics endpoint, no alerting rules, and `/api/health` does not check web-store writability or disk space. Define SLOs, emit structured JSON logs, add Sentry (or equivalent) for server and client errors, and alert on: audit write failure, chain verification failure, pending-gate age, job queue depth, 5xx rate, and disk usage.

### Q-19 · No data subject / retention automation
`docs/records-retention.md` is thoughtful, but there is no code that purges expired sessions, expired invites, used reset codes, or old notifications on a schedule; expired sessions are only removed when a token is presented. There is no account deletion or data export endpoint for officers or suppliers. Add scheduled housekeeping and an explicit erasure/export path (with audit) before a pilot.

### Q-20 · Minor authorization and operational nits
- `GET /api/settings/rules` requires only a session, not `manage_rules` or `view_oversight` (`src/app/api/settings/rules/route.ts:19`).
- `POST /api/admin/judge-reset` spawns a detached `bun scripts/judge-proof.ts` from a web request; no input injection, but unbounded process spawning and a demo-only surface in production (`src/app/api/admin/judge-reset/route.ts`).
- `/api/team` PATCH lets an OWNER demote another ADMIN without a second approver; acceptable, but the governance log is the only friction.
- The checklist store is keyed only by tender reference (`contract-checklist:<ref>`), so it is shared across workspaces and has no per-user audit.
- Dual approval depends on parsing a monetary value from `inputs.value|amount|awardValue`; a gate whose inputs omit a parseable value silently skips the threshold (`index.ts:gateValue`, `requiresDualApproval`).
- `inviteResponse` exposes the invite code to any `manage_people` caller (expected), but there is no rate limit on code validation at registration beyond the per-IP register limit.
- `logout` is a POST with no CSRF token; SameSite=Lax is the only protection. Add an Origin check for defense-in-depth.

### Q-21 · Frontend modularity and performance risk
`dashboard.tsx` is 11,219 lines and `cycle-view.tsx` is 8,159 lines. Both are client components in a single hash-routed page (`src/app/page.tsx`), so the landing, auth, and workspace all share one bundle graph. This is a maintainability and performance risk: slow iteration, difficult review, large first-load JS, and no route-level code splitting for the workspace. Split by section (overview, cycle, committee, oversight, integrations, assistant) with lazy boundaries; measure first-load JS and interaction latency before/after. No performance budget or Lighthouse check exists.

### Q-22 · Accessibility is thoughtfully attempted but unverified
Positives: 479 `aria-label`s, skip links in dashboard/admin/supplier console, focus trapping and roving tabindex helpers (`src/lib/a11y.ts`), reduced-motion handling, 4/4 `<img>` with `alt`. ## 8. Domain and AI-specific observations

**Strong:** deterministic rule path, planner safety floor (parsing may be added, never removed), source citations with quote-existence checks, redaction before hosted calls, residency policy, model attribution stored verbatim, template fallback labelled, injection screening on bid text, and a read-only desk assistant whose only write is a consent-staged review assignment. The “agent prepares, committee awards” boundary is enforced in code, not just prose.

**Gaps:**
- The injection screen is a five-pattern regex list (`src/lib/injection-screen.ts`); it is a useful tripwire, not a defense. The real defense is that tool calls are allowlisted and authorized server-side — keep that invariant and add tests for indirect injection through retrieved documents.
- “Quote exists in the cited bid” is verified; “the quote supports the finding” is not. The README says this; the UI should say it at the point of decision, not only in the report footnote.
- Model evaluation is single-labeller and the independent review packet is unreturned (documented). No human time-saved or recall study exists (documented).
- `syncNotificationsForUser` fetches `/api/gates` and `/api/cycle/deadlines` without the workspace header, so the sidecar defaults to `demo`; it will miss real-workspace gates and may surface demo rows. Fix the scoping or remove the fallback.
- The deterministic rule path is the strongest part of the product; invest there (more rule packs, clearer evidence) before expanding model autonomy.
